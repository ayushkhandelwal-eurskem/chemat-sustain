1 · Overview

1. Platform Overview

CheMatSustain is a research data portal for selected chemicals and nanomaterials. It converts heterogeneous test-specific Excel workbooks into a consistent five-section data contract, stores the result with ownership and publication metadata, and presents it through both human-oriented scientific viewers and scope-controlled machine APIs.

19
registered scientific test types
5
independently releasable data sections
3
interactive roles: public, team, admin

1.1 Core capabilities

  • Upload and retain source Excel workbooks for scientific traceability.
  • Parse each assay/instrument format with a dedicated Python parser.
  • Normalize parser output into a stable JSON contract.
  • Browse data by work package, CMS material identifier, test category, and test type.
  • Render specialized tables, charts, statistics, images, and CSV downloads.
  • Publish a test while independently selecting which scientific sections are public.
  • Support authenticated public viewers, internal team users, administrators, and machine clients.
  • Apply resource grants, API scopes, tenant context, access logs, and operational security gates.

2 · Architecture

2. Architecture and Technology Stack

Figure 1. Production-oriented component architecture. Solid arrows represent principal request/data paths; dashed arrows represent governance and operational interactions.

2.1 How to read the architecture

  1. Human users access one HTTPS origin. Nginx sends page requests to Next.js and rewrites /api/* to FastAPI.
  2. Machine clients use separately issued HTTP Basic credentials against /api/v1; scope and resource checks occur on every request.
  3. FastAPI owns application contracts, parsing orchestration, role checks, release projection, resource filtering, and audit writes.
  4. PostgreSQL stores searchable identifiers, normalized JSON sections, users/sessions, ownership, grants, protocols, and audit history.
  5. Persistent volumes preserve original workbooks and SOP/protocol files separately from container images and database rows.
  6. CI/CD deploys only after secret, static, dependency, tenant-isolation, SBOM, and container-image checks succeed.

2.3 Broader context

Laboratory interoperability

Partners can continue producing familiar assay-specific workbooks. Dedicated parsers absorb layout differences and emit one application contract.

Scientific interpretation

Specialized viewers retain domain meaning that a generic JSON browser would lose: units, replicate context, plotted series, uncertainty, and statistical tables.

Governed dissemination

A record can be discoverable as public while raw, processed, final, statistical, or condition sections remain independently withheld.

Human and machine reuse

The portal optimizes comprehension; the /v1 interface supports authorized pipelines without sharing browser sessions or administrator credentials.

Architectural boundary. PostgreSQL does not contain the uploaded workbook bytes. The tests.file_path value links a database record to the persistent research-data volume. Public responses always omit this internal server path.

3.7 Tenant and resource controls

Defense in depth. Machine API reads combine (1) credential authentication, (2) scope checks, (3) explicit user/resource profile checks, (4) transaction-local organization context, (5) PostgreSQL RLS policies, and (6) audit events. Transaction-local set_config(..., true) prevents tenant context leaking through the connection pool.
Operational migration note. Repository guidance states that legacy ownership reconciliation must be completed before the production runtime database connection is switched from the current owner role to the least-privilege, RLS-enforcing chemat_app role. RLS policies and CI tests exist, but operators must verify the live connection role and ownership migration status rather than infer it from source code.

Operational recovery controls

  • PostgreSQL data persists in the pgdata Docker volume.
  • Research workbooks and protocol files use host bind mounts so image rebuilds do not erase them.
  • The deploy script refuses to proceed over tracked server edits, applies reviewed migrations, verifies mounts, rebuilds images, and checks direct plus Nginx health.
  • API documentation endpoints are fail-closed and the deployment explicitly verifies that /docs, /redoc, and /openapi.json are not published.

4.3 Password and session behavior

  • Passwords are bcrypt-hashed; schemas require at least 12 characters for account creation/reset.
  • Privileged user and admin roles require emailed OTP after password verification.
  • The session cookie is HttpOnly, Secure by default, SameSite=Lax, and has a seven-day maximum age.
  • Unsafe cookie-authenticated requests require an allowed Origin; responses receive request IDs, no-store, and security headers.

5 · Worked implementation

5.3 Backend Parser Logic

1Open and normalize

TBParser.__init__() loads the workbook with formulas resolved (data_only=True) and selects Test_conditions. Helpers normalize human labels into snake-case keys, parse Excel/date variants, replace decimal commas, and return None for unusable numeric values.

normalize_key(label): lowercase → replace non-alphanumeric runs with "_" excel_date_to_string(value): datetime | Excel serial | known string formats → YYYY-MM-DD _safe_float(value): decimal comma → decimal point → float; invalid → None _safe_str(value): trim non-empty values

2Extract typed scientific structures

Dataclasses define the parser’s output vocabulary—WorkPackageData, MaterialData, DispersionData, CellLineData, TreatmentData, raw/processed blocks, and final results. Extraction methods return dictionaries using asdict().

extract_work_package_data() scan first six columns for label/value rows map normalized labels to wp, partner, full name, acronym, type, endpoint, SOP read scientist names/emails; retain email only when regex-valid extract_material_data() map Test_conditions rows 26–43 to identifiers, chemistry, batch and stock metadata extract_raw_data() for each sheet whose name starts with "raw_data": find matching "Processed data_<suffix>" collect chamber labels and % cell death from columns D:G collect protocol/instrument values and assay notes

3Assemble one canonical payload

parse_all_data() → { "test_details": {work_package, material, dispersion, cell_line, treatment}, "replication_metadata": [...], "raw_data": raw_runs, "replications": raw_runs, # compatibility key consumed on upload "processed_data": processed_runs, "final_results": final_summary, "statistical_analysis": statistics, "parser_warnings": [...] # only when present }
Important mapping. The upload controller’s build_payload_from_parse() writes file_data["replications"] into the database raw_data column. TB deliberately emits both raw_data and replications with the same list for compatibility with this canonical upload path.
5 · Worked implementation

5.4 Upload, Persistence, and Read Projection

Administrator upload sequence

  1. POST /tests/ requires the administrator role.
  2. validate_excel_filename() accepts only .xlsx or .xls.
  3. get_parser("TB") resolves parse_excel_tb from the centralized 19-test registry.
  4. save_uploaded_file() sanitizes the timestamped name and writes the workbook under the persistent research-data mount.
  5. The parser runs. Any parser failure deletes the just-saved file and returns a non-sensitive 400 response.
  6. clean_for_json() recursively converts dates, decimals, tuples, and unsupported values into JSON-safe primitives.
  7. TestService.create_test() rejects a duplicate locator triple, validates private/release consistency, commits the row, and refreshes it.
  8. If database creation fails, the controller removes the saved workbook so no orphan is left.

5.5 TB Frontend Viewer Logic

Fetch and state

TBDataViewer receives the decoded route values and requests the exact test record. React state tracks the response, loading/error state, active tab, and selected run.

useEffect([work_package, element, test]): POST /tests/listings { work_package_name, element_cms_id, test_name } setData(response.data) state = { data, loading, error, activeTab, selectedRun }

Release-aware tab construction

TB is directly safe for partial public releases. It derives available tabs from response values; Test Conditions additionally checks release_test_details !== false because the public response may contain only the header metadata envelope.

6 · Maintenance

6. Operations and Extension Guide

6.1 Adding a new test type

  1. Define the canonical test identifier and keep it identical across create options, parser registry, URL dispatch, and viewer registry.
  2. Create a parser under backend/parsers/ that returns all five canonical sections (use explicit empty/unavailable structures where a section is unsupported).
  3. Add the parser function to PARSERS in backend/api/controllers/test.py.
  4. Create a null-safe TypeScript viewer under frontend/src/components/tests/.
  5. Register the viewer in RoleAwareTestViewer.tsx and add catalogue display metadata.
  6. Add the test option to CreateTestModal.tsx.
  7. Test every independent public section flag and all relevant combinations; never infer a section’s release from another section’s presence.
  8. Run parser tests, public projection tests, backend suite, ESLint, TypeScript, Next.js build, Compose validation, and security workflow.

6.2 Parser design rules

  • Normalize spreadsheet variability at the parser boundary.
  • Use safe conversions and preserve missing values as null/None.
  • Return stable typed keys; do not make viewers understand workbook coordinates.
  • Record optional/missing scientific sections explicitly rather than crashing.
  • Avoid logging complete scientific payloads in production; treat source data according to classification.

6.3 Database change rules

  • Use reviewed, idempotent migrations outside development; production auto-DDL must remain off.
  • Back up and restore-test before ownership/backfill or destructive changes.
  • Preserve fail-closed behavior when tenant context, release state, or credentials are missing.
  • Keep heavy JSON out of list/index queries; fetch full payload only for one authorized record.
  • Coordinate DB rows and persistent files to avoid dangling paths or orphan files.
  • Do not store plaintext passwords, client secrets, OTPs, authorization headers, or tokens in logs/audit metadata.

System summary. CheMatSustain uses a hybrid database architecture to preserve scientific flexibility without sacrificing governance: source workbooks remain durable, parser-specific knowledge is isolated in backend modules, canonical JSON enables common APIs, specialized viewers retain scientific meaning, and layered identity/release/tenant controls constrain who can see what.
